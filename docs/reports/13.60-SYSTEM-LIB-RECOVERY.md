# 13.60 System-Library Recovery for WebKit Analysis

How to recover a decrypted WebKit module image from a jailbroken lower-firmware
PS5, and what that image can (and cannot) tell us about the 14.10 chain.

## Why this exists

Stage 2 of the 14.10 chain needs a real WebKit binary to ground the
CVE-2026-43720 analysis in an actual PS5 build: struct layouts, allocator
behaviour, Canvas2D internals, and unwind data. 14.10 has no code execution
yet, so its own `libSceNKWebKit2.sprx` cannot be read. A jailbroken console on
7.61-13.60 can supply the decrypted module from the live process instead. On
13.60 the same module is named `libSceNKWebKit.sprx`.

Everything below was validated on retail PS5 hardware running firmware 13.60
with the usual jailbreak stack (kstuff, elfldr payload loader) and was
cross-checked independently, as described under Verification.

## Target

| Property | Value |
|----------|-------|
| On-disk file | `/system_ex/common_ex/lib/libSceNKWebKit.sprx` |
| Container | SCE SELF, 26,107,749 bytes, magic `54 14 f5 ee` (encrypted on disk) |
| Loaded by | `SceNKUIProcess` (NPXS40087) and `SceNKNetworkProcess` |
| Related modules in the same directory | `libSceNKWeb.sprx`, `libSceJsc.sprx`, `libSceNKWebKitRequirements.sprx`, `libScePosixForWebKit.sprx` |

The same pipeline should apply to those sibling modules and to other
lower-firmware versions that still have a usable jailbreak; on 13.60 only the
module above was validated end to end.

## Key observation: the SELF predata holds the plaintext ELF headers

A SELF container stores the loader-facing ELF header and program headers in
plaintext metadata. For this module:

- offset `0x1A0` in the `.sprx`: the 64-byte ELF64 header
- offset `0x1A0 + e_phoff`: the original program headers (56 bytes each)
- `e_type = 0xFE18` (`ET_SCE_DYNAMIC`), `e_machine = 62` (x86-64)
- `e_phnum = 14`, `e_shoff = 0`, `e_shnum = 0` (stripped, no section headers)

No decryption keys are needed to read this metadata; the segment *data* is what
requires the live console.

PT_LOAD layout of the 13.60 image:

| idx | p_offset | p_vaddr | p_filesz | p_memsz | flags | role |
|-----|----------|---------|----------|---------|-------|------|
| 0 | 0x4000 | 0x0 | 0x2ADB10E | 0x2ADB10E | X | `.text` |
| 1 | 0x2AE0000 | 0x2ADC000 | 0x653A70 | 0x653A70 | R | `.rodata`, `.eh_frame` |
| 3 | 0x3134000 | 0x3130000 | 0x2208F8 | 0x224000 | RW | RELRO / relocated data |
| 7 | 0x3358000 | 0x3354000 | 0x11090 | 0x3B9E8 | RW | data + bss tail |
| 8 | 0x336B9F0 | 0x338F9F0 | 0x5F4178 | 0x5F4178 | none | loader-only metadata |

The image ends at `max(p_offset + p_filesz) = 0x395FB68` (60,160,872 bytes).
Text is mapped execute-only (`PF_X`, no read flag) on PS5.

## What the loader does that matters

- PT_LOAD idx 8 (`p_flags = 0`) contains `PT_DYNAMIC`, `PT_NOTE` and the
  relocation metadata. It is unmapped after relocation (observed: absent from
  the VM map of every running process that has the module loaded), so a memory
  reconstruction cannot recover `.dynamic`, `.dynstr`, `.dynsym` or
  `.rela.*`; expect that range to be zero-filled. This is normal and is not a
  dump error.
- The mapped image is the remaining four PT_LOADs. The module mapping base
  reported by the loader equals the ELF load base plus the lowest `p_vaddr`
  (here 0, so base is the mapping base itself).
- Data segments hold runtime values: ASLR-rebased pointers and mutated state.
  They are process snapshots, not static file bytes.

## Pipeline

1. Resolve the loaded module in a target process with the jailbreak kernel
   helpers: `kernel_dynlib_handle(pid, "libSceNKWebKit.sprx", &handle)` and
   `kernel_dynlib_mapbase_addr(pid, handle)`.
2. Read the plaintext ELF header and program headers from the on-disk SELF
   predata (offsets above) and use them as the output ELF's header/phdrs.
3. For each PT_LOAD with `p_filesz > 0`, read the live bytes at
   `load_base + p_vaddr` with `kernel_proc_copyout(pid, addr, buf, len)`
   (read-only; the target process is never written to), and write them at
   `p_offset` in the output file.
4. Pull the image off the console (FTP is sufficient; no console or PII data
   is needed).

`kernel_proc_copyout` is available to payloads built with the PS5 payload SDK
plus the kstuff kernel helpers. The same read primitive is what makes the
reconstruction possible without touching the target.

## Verification

Each check below was run on device and is cheap to reproduce:

1. **Metadata self-consistency** - output ELF header and all program headers
   byte-equal the SELF predata copy.
2. **Cross-process identity** - reconstruct the same module from two different
   processes that map it (NKUI and NKNetwork). `.text` and `.rodata` must be
   byte-identical; ASLR moves the base, not the bytes. Relocated data differs
   by the module slide, plus runtime-mutated state.
3. **Code validity** - disassemble `.text` (capstone or objdump): invalid
   instruction count, direct call/jump targets staying inside `.text`, and
   prologue alignment.
4. **Unwind consistency** - `.eh_frame_hdr` FDE count matches
   `PT_GNU_EH_FRAME` file size, and sampled FDEs resolve into `.text`.
5. **Live spot checks** - compare random 16-byte samples read from the target
   process with the assembled file.
6. **Layout relations** - file size equals `max(p_offset + p_filesz)`, and
   `p_offset % p_align == p_vaddr % p_align` for every PT_LOAD.

Fingerprints of the validated 13.60 image, useful for cross-checking another
console's dump (hashes are of the segments, not of any redistributable file):

`-//W3C//DTD XHTML 1.1//EN`, `Automation.evaluateJavaScriptFunction`.

## Pitfalls

- `kernel_proc_copyout` returns success (0) even when the target page is not
  mapped; it can return zeros or uninitialised bytes. Cross-process identity
  and live samples are the integrity checks that catch this.
- Mapped but non-resident pages may read as zero. `.eh_frame` and string
  content are quick sanity checks against systematic gaps.
- PT_LOAD idx 8 is unrecoverable from memory. For static analysis this is
  usually acceptable (`.text`/`.rodata` are unaffected), but anything that
  needs dynamic symbol or relocation metadata will fail.
- Do not trust absolute addresses or data-segment contents across loads or
  firmware versions.
- `e_type = 0xFE18` is not accepted by some generic ELF loaders. Patch
  `e_type` to 3 (`ET_DYN`) in a copy for IDA/Ghidra/objdump if needed; keep the
  original header for provenance.
- The recovered artifact is Sony code. Do not commit it to this repository or
  post it publicly; share privately with researchers who need it for analysis.

## Relevance to the 14.10 chain

- The 13.60 image is the WebKit generation immediately before 14.10. It gives
  real PS5 text, rodata and unwind data to ground WK-1400 source claims, the
  CVE-2026-43720 write-up, and the planned code-exec stage.
- Do not copy offsets, NIDs or function addresses between firmware versions.
  Use the image for structure and semantics; symbol/offset work still has to be
  validated against the 14.10 binary once it is reachable.
- The same recovery pipeline can supply the sibling NK/WebKit libraries from
  lower-firmware consoles, which is useful for comparing engine evolution
  between builds.

## Boundaries

This work is on personally owned retail hardware, for research and
interoperability analysis. No binaries, probes, private IP addresses, console
identifiers or PII belong in this repository; the artifact should be exchanged
privately between researchers.
